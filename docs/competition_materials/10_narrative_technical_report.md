# 智安护居叙述性技术总报告

# 1 项目概述

## 1.1 项目背景

居家老人安全并非单一“是否跌倒”的判断问题。跌倒发生前，步态速度、步长、身体稳定性和神经运动模式可能逐步变化；跌倒发生时，需要从持续视频中快速识别人、姿态和动作状态；日常通信环境中，摄像设备的音轨还可能包含索要验证码、诱导转账、冒充公检法等诈骗话术。三类问题的数据形态、时间尺度和风险语义明显不同：跌倒检测需要秒级连续判断，步态与运动功能评估需要一段完整行走样本，诈骗识别需要跨语句上下文。

智安护居以一台真实 EZVIZ H6c 作为居家感知入口，将视频、音频、设备状态和算法结果纳入同一平台。系统没有把所有算法堆入 Web 后端，而是建立设备接入、共享媒体、实时算法、批处理评估、结果管理和页面展示的清晰边界，使模型可替换、设备凭据不进入算法服务、单项算法故障不拖垮基础平台。

## 1.2 项目意义

平台当前形成了一个可继续验证的安全链路。事前环节通过直线行走视频恢复人体运动，计算步态参数，并分别以 KINECAL ST-GCN++和 MotionCLIP提供跌倒史队列分级与神经退行性疾病相关运动功能表征；事中环节持续读取摄像机视频，以人物检测、COCO17姿态和时序骨架模型识别跌倒；风险结果经统一合同进入 Redis 和 WebSocket，在首页、检测页和事件页呈现。诈骗模块并行读取真实音轨，以本地 ASR、规则证据和可选本地大模型识别可疑语义。

当前实现的价值首先在于打通真实设备到算法和页面的工程闭环，并对不可用、低置信和未校准结果采用明确语义。它尚未建立短信、电话或医疗处置流程，也未完成三类算法的独立临床验证，因此正式结论应聚焦“可运行、可追踪、可扩展的研究系统”，不扩大为医疗诊断或成熟预警产品。

## 1.3 核心创新

第一个技术特点是同一摄像设备上的双媒体路径。浏览器需要低延迟交互和官方控制能力，因此采用 EZOPEN；Ubuntu算法服务无法通用解码私有协议，故 Backend申请临时HTTP-FLV，由共享中继统一解码HEVC、低延迟编码H.264并通过RTSP扇出。两条路径共享设备源但针对消费端优化，同时以Backend隔离AppSecret和临时地址。

第二个特点是把实时事件检测与长期运动功能评估分离。实时链以COCO17二维骨架和STGCN-Extend完成秒级状态机；评估链以MeTRAbs、GVHMR恢复更完整的三维运动，再由KINECAL与MotionCLIP分别回答“跌倒相关队列特征”和“神经运动功能偏离”。这种分工避免把一个分数同时解释为跌倒概率和疾病风险。

第三个特点是统一且带真实性标记的结果合同。各模型只能发布`AlgorithmResult`，其中任务、时间、模型版本、分数、等级、metadata和`simulated`都有约束。开发pipeline test必须标记为模拟数据，业务页面只消费真实结果；无人、低置信、媒体断开也不能被自动解释为正常。

# 2 系统总体架构

## 2.1 整体架构

感知层由H6c提供设备状态、H.265视频和AAC音频。设备与数据接入层由EZVIZ Adapter、Token Manager、Stream Service和共享媒体中继组成；它把供应商字段映射为CareShield设备/媒体合同，并将敏感凭据约束在Backend。AI层由多个独立Worker组成：实时跌倒Worker、步态/GVHMR批处理Worker、MotionCLIP Worker、KINECAL Worker和诈骗Worker。服务与数据层由FastAPI和Redis承接，PostgreSQL当前仅作为已部署的基础设施预留。实时通信层使用单一WebSocket；应用层以Vue页面展示总览、设备、风险评估、检测和事件。

Backend与AI Worker分离的原因是职责和运行环境均不同。Backend负责稳定API、安全鉴权、状态聚合和协议适配，不应加载CUDA模型；实时Worker使用PyTorch、Ultralytics和PyAV，步态Worker还包含TensorFlow/MeTRAbs与GVHMR，MotionCLIP和KINECAL又依赖各自checkpoint匹配环境。独立容器让模型替换不改变前端合同，也减少依赖冲突。

#### 实现依据

- `docker-compose.yml`
- `backend/app/main.py`
- `shared/python/careshield_contracts/`

## 2.2 数据流与服务协同

设备查询时，Backend以AppKey/AppSecret申请AccessToken，在过期前五分钟刷新，并在上游返回失效码时主动重取。浏览器直播会话只在显式启用后创建，响应设置no-store；官方EZUIKit在首帧事件后切换LIVE。服务端只从内部鉴权接口取得临时媒体，由media-relay读取一个HTTP-FLV源，转换HEVC位流后发布到私有MediaMTX路径。实时跌倒与诈骗Worker作为读者，批处理评估通过短时fMP4缓冲按触发时间截取。

算法结果经Bearer鉴权进入Backend。Redis以短TTL保存Worker心跳，以较长TTL保存各任务latest result，并用有界列表记录有意义的跌倒状态和真实风险事件。Realtime Hub把同一envelope广播给浏览器；Vue客户端集中处理解析、断线指数退避和全局最新状态，避免每个页面各建一条连接。

## 2.3 多模态AI分析框架

视频实时链关注“当前是否发生跌倒”，批处理视频链关注“行走表现及其参考分级”，音频链关注“对话中是否出现诈骗证据”。三条链不共享模型对象，却共享设备ID、时间戳、风险等级和真实性语义。当前没有把多模态结果再送入一个总决策模型；首页的综合态势只是对各条真实结果进行安全优先级展示。这一点避免把工程聚合误称为经过训练的多模态融合算法。

# 3 核心算法

## 3.1 步态参数提取

评估视频首先经过完整性检查和连续人体片段选择。MeTRAbs输出17点三维骨架和图像坐标，短暂漏检可在同一连续段内插值，长时间无人则切段。换序、中心化和坐标变换后的骨架输入Gait Transformer，步态相位经Kalman平滑得到左右脚跟着地和脚尖离地事件。时域参数由事件帧差和源FPS计算，空间参数由三维踝、腕和躯干轨迹估计，稳定性参数进一步利用eCOM、XCoM和接触支撑区。

算法实际计算28项参数，页面重点展示8项，同时保留完整信息。参数缺失保持null并说明事件不足，质量合同记录有效姿态、全身可见、插值比例、最大缺失和步数。由单目骨架推导的米制空间量存在尺度误差，应与质量和模型结果共同解释。

#### 实现依据

- `fall-risk-worker/pipelines/visionmd/`
- `fall-risk-worker/app/services/parameter_catalog.py`

## 3.2 基于 MotionCLIP 的神经退行性疾病相关运动功能评估技术

GVHMR把选中的行走片段恢复为SMPL-X姿态和相对平移。适配器将这些参数转换为MotionCLIP所需的rotation-6D运动张量，以30 FPS划分2秒窗口。Transformer encoder将整段动作映射到语义空间，健康参考距离描述当前embedding与训练期健康参考的余弦偏离；相对向量再与八类运动概念的文本prototype比较，形成步幅、速度、抬脚、摆臂、步频、步宽、横向稳定和弯腰姿势的等级概率。

模型没有输出某种神经退行性疾病的诊断概率。低中高只是健康参考距离在CARE-PD-like训练分区阈值上的区间。可解释性一部分来自语义prototype和相似度，另一部分来自系统同时展示的步态参数与质量结果。本地Qwen只把这些结构化事实组织为专业中文，输出经过数字、等级、长度和诊断措辞校验；失败时回退确定性模板，不改变分类。

#### 实现依据

- `motionclip-worker/app/`
- `fall-risk-worker/app/adapters/risk_explanation.py`

## 3.3 跌倒风险评估技术

跌倒风险主模型使用GVHMR世界系21点骨架。适配器建立H36M-17顺序、构造胸点、转换到近Kinect坐标，按骨盆中心化并做序列尺度标准化，最后采样为`[3,120,17,1]`。ST-GCN++以人体关节图的自连接、向心和离心邻接在空间维聚合信息，多尺度时间卷积在不同膨胀率上提取节律变化。池化特征与标准化时长、3米正面行走action embedding共同进入adapter和三分类头。

模型输出NF、FHs、FHm三类，页面映射为低、中、高跌倒风险并显示置信度。该标签本质对应训练队列的无跌倒史、单次跌倒史和多次跌倒史，不是未来事件概率。当前checkpoint对单一3米步行高风险样本的召回记录为0/7，且训练划分可能存在subject leakage，因此低风险不能排除危险，必须结合步态参数、运动功能和专业评估。

#### 实现依据

- `kinecal-risk-worker/app/`

## 3.4 实时跌倒检测技术

实时Worker从共享媒体读取H.265帧，以15 FPS目标率采样。YOLO人物检测保持横卧或关键点缺失时的“人存在”证据，YOLO Pose输出COCO17。几何融合和轻量追踪为每个人维护独立ID与2秒缓存；全图姿态漏检时，可在真实人物框裁剪上重试，并对横向裁剪尝试90度方向后映射回原图。系统不会复制旧骨架冒充当前关键点。

可靠窗口经重采样形成STGCN-Extend输入。模型先利用时空图卷积编码部分观察，预测25个未来姿态位置，再对观察与预测组成的100帧序列进行二分类。class-1 softmax是未校准的Fall Score。状态机将连续分数转为正常、疑似、跌倒、恢复，并以告警锁存和发布节流避免瞬时抖动与消息洪泛。结果到达Backend后写Redis并由WebSocket驱动页面；分析MJPEG来自模型实际处理帧，与浏览器EZOPEN画面不承诺逐帧同步。

#### 实现依据

- `ai-worker/app/fall_detection/`
- `ai-worker/app/services/fall_detection_service.py`

## 3.5 诈骗识别技术

诈骗Worker只消费共享流音频。AAC解码后转为16 kHz单声道PCM，能量端点把连续音频切为有限语句；本地Faster-Whisper产生中文文本和工程置信度。检测器在短期上下文中累积关键词、关键行为组合及同音误识别条件，可选本地Qwen以JSON复核语义。规则和LLM证据经过衰减与滞回，形成正常、可疑、告警和高风险状态。

该路径避免将家庭音频发送到云端：原始音频不保存，完整对话只在有限内存中保留，发布到Redis和页面的是脱敏摘要。当前证据分数不是诈骗概率，系统也缺少正式标注语料的准确率测试。工程上已形成真实媒体、ASR、判定、实时发布和页面告警链，算法有效性仍需专门实验。

# 4 软件系统实现

## 4.1 前端应用

Vue应用以统一布局组织首页、跌倒风险、跌倒检测、诈骗风险、事件、设备、算法和系统页面。REST用于初始状态、任务和历史，WebSocket用于实时结果，EZUIKit专门负责直播。页面坚持状态与颜色双重表达；算法不可用、无人和低置信时显示明确原因。开发pipeline test只在算法诊断页显示。

## 4.2 后端服务

FastAPI把路由、服务和EZVIZ Adapter分层。设备原始JSON在服务层映射为CareShield Schema，内部AI接口使用共享Bearer Token，异常只返回安全摘要。Backend代理风险评估任务和产物，浏览器不获得Worker地址、宿主路径或临时标准流。

## 4.3 AI推理服务

实时与批处理按依赖和负载分成多个Worker。每个Worker通过health、capability和heartbeat报告真实生命周期。模型权重只读挂载并在关键服务校验checksum。无GPU、模型缺失、媒体异常不会使Backend崩溃，而是把能力降为unavailable/error。

## 4.4 实时通信与数据管理

Redis不是训练数据仓库，而是实时状态层。Worker TTL防止进程失联后永久显示在线；latest result支持页面重载恢复；风险事件按告警生命周期去重。WebSocket只暴露一条通道，模型更换不需要增加前端连接。PostgreSQL虽然健康运行，但尚未承担受试者、评估或事件业务数据。

## 4.5 萤石开放平台接入

Token Manager根据官方expireTime管理AccessToken，并处理失效重试。设备列表、详情、HLS诊断、HTTP-FLV算法源和EZOPEN浏览器会话都经同一Adapter边界进入系统。AppSecret从不离开Backend；EZOPEN因官方SDK要求而在显式开启时向可信浏览器提供运行期Token，响应禁止缓存且前端不持久化。

# 5 系统部署与运行

Docker Compose定义基础服务、算法服务、健康检查、私有网络、GPU和只读模型卷。普通服务可在CPU模式启动；算法能力按实际环境退化。标准运行从准备`.env`、子模块和授权模型资产开始，以`docker compose up -d --build`启动，再依次验证health、设备、中继、Worker、Redis、WebSocket和页面。停止时不删除volume，避免丢失评估记录和本地模型。

# 6 实验与实测情况

真实媒体链已有HEVC 1920×1080约15 FPS和AAC 16 kHz单声道证据；5秒H6c行走片段已生成150帧GVHMR骨架、参数和两种网格视频；实时跌倒模型在保存的88样本split上重现88/88标签，但这只验证迁移兼容性。MotionCLIP阈值文件记录141 walks、83 subjects和训练阈值选择macro-F1 0.505334；KINECAL说明记录3米步行held-out accuracy 74%，同时高风险recall为0/7。后两项缺原始逐样本输出，不适合作为系统效果宣传。

当前最缺的是按受试者隔离的跌倒检测和跌倒风险外部测试、诈骗标注语料、端到端告警延迟、每小时误报和长期稳定性。任何Accuracy、F1、AUC或临床结论都应在完成这些补测后再进入正式报告。

# 7 系统完整运行流程

系统启动后，Backend建立设备适配与Redis连接，各Worker定期发送带TTL心跳。media-relay选择在线H6c并申请临时HTTP-FLV，将HEVC/AAC发布到内部RTSP。浏览器独立申请EZOPEN会话显示实时画面。实时跌倒Worker解码帧、检测和追踪人物、提取COCO17、形成时序窗口并执行STGCN-Extend；诈骗Worker解码音轨、分句、ASR和语义判定。两者发布统一AlgorithmResult，Backend更新Redis并广播WebSocket，页面据此更新状态和告警。

当用户创建跌倒风险评估时，系统保存受试者信息，从环形缓冲按触发时刻取片或接收上传MP4。VisionMD生成步态事件、参数和骨架视频，GVHMR生成SMPL-X参数、世界骨架和网格视频；KINECAL对世界骨架分级，MotionCLIP对运动序列形成健康参考偏离和概念解释。manifest保存任务、质量、产物和结果，用户可从历史记录回看。

# 8 当前完成度与可验证能力

设备查询、浏览器直播、共享媒体、统一实时通道、人物/姿态分析、批处理产物和基础页面属于可验证工程能力。实时跌倒、KINECAL、MotionCLIP和诈骗模型已经真实接入或具备完整实现，但在正式算法性能层面仍缺充分实验。通知处置、用户权限、业务数据库和医疗校准尚未实现。最准确的阶段结论是：系统已形成真实设备驱动的多模态研究平台与三类算法基线，具备现场演示和继续验证条件，尚不具备替代临床诊断或独立安全决策的证据。
